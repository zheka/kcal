# AI outside the app: Gemini and a Drive folder

The plan for where photo recognition goes: out of kcal and into the Gemini app, which gets its
context from a Google Drive folder kcal keeps, and hands its result back through the share sheet.

Status (2026-11-27): **the direction is agreed, nothing built.** The AI code stays in the app and
the lab for now: first comes the work needed either way (see [Order of work](#order-of-work)).
Where [dishes-and-ai.md](dishes-and-ai.md) assumes a model called from kcal, this plan replaces it
once the AI is removed.

## The idea

- **kcal has no AI.** No model calls, no API keys, no AI context or request logs. Everything in
  the app works offline, with no model.
- **Gemini does the recognition.** A photo of a meal or a product goes to the Gemini app, which
  answers with JSON in kcal's **exchange format**. The JSON is shared to kcal
  ([share-target.md](share-target.md)), which checks it, matches it against the library, offline,
  and opens it for review before anything is saved.
- **kcal keeps a Drive folder with everything Gemini needs**: the library, what I usually eat,
  the instructions and the exchange format. In Gemini I only point at the folder.

Why: the app stays offline and simple (no keys, quotas, costs, or screens around a model); Gemini
is better at the hard part (photos, follow-up questions, corrections in a conversation); the prompt
can change without a release of kcal.

## The folder

kcal writes it; nothing else does. Files are written for a model to read, not copied from the
backup:

- **`README.md`**: what each file is and what to answer with. The folder explains itself, so it
  works with whatever points at it (a Gem, a Skill, a file mentioned in a chat, another assistant):
  Gemini's features for this change often, and nothing depends on one of them.
- **instructions and exchange format**: generated by kcal for its own version of the format. The
  app that checks the reply writes the prompt for it, so the two never drift apart.
- **library**: compact, names first, with units and portions; ids only where a reply refers to
  them.
- **recent**: what I usually eat, as a short summary, not every meal.
- **backup**: the full backup, as its own file. It is not meant for the model: it gives the data a
  copy off the phone, which kcal doesn't have today.

## Export first, sync later

- **Export (first):** kcal writes the folder after a change, while it is open and online. One way
  only: the folder is never read back. This serves Gemini and gives a backup.
- **Sync (later):** two devices, no server in between. The shape agreed in
  [design.md](design.md#changes): records get `updatedAt` and tombstones; each device writes a file
  of its own changes and every device merges all of them, so no two devices ever write the same
  file.

Neither is a place the store keeps data: the export follows the store's changes and writes files.

## Technical notes

- **Access:** the `drive.file` scope: kcal sees only the files it created. It is non-sensitive, so
  Google doesn't need to review the app. Needs a Google Cloud project, an OAuth client for
  `zheka.github.io`, and the consent screen.
- **Sign-in in a PWA:** Google's browser sign-in gives an access token for an hour and no
  long-term token. So the export runs while kcal is open, and sometimes needs one tap to sign in
  again.
- **Gemini reads Drive files at their latest version**, so the folder needs no re-uploading.
- **Privacy:** the food log sits in my Drive and is read by Gemini under my account; Gemini's
  activity setting decides whether those conversations may be used for training.
- **Replies drift:** Gemini may rename fields or put prose around the JSON. kcal is strict about
  what it accepts and forgiving about how it arrives: it finds the JSON in text or a code block,
  checks it, and when it refuses, says why.
